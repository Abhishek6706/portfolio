01 ML-Based Delivery Time Estimation in progress

A promised delivery time is only useful if it holds. This system breaks each delivery into three sequential legs and predicts each one with its own XGBoost model. The three predictions are added up into the final estimate and served over a REST API. The first baseline delivers 73% of orders within the promised window.

04GridSearchCVhyperparameters
05Aggregatesum → final ETA
06FastAPIREST predictions
PostgreSQLSQLAlchemyXGBoost GridSearchCVPandasEDAFastAPI
  1. Data retrieval from PostgreSQL

    Order and delivery history lives in PostgreSQL. I query it through SQLAlchemy ORM models instead of hand-written SQL, so the same pipeline can pull training data and serve inference.

    › PostgreSQL · SQLAlchemy ORM · Pandas
  2. Exploratory data analysis

    I used EDA to find which order, location, and timing attributes actually move delivery time. Those findings decided the feature set before any model was trained.

    › Pandas · Matplotlib / Seaborn · NumPy
  3. Three sequential components

    A single end-to-end regressor would blur very different stages together. Instead, delivery time is split into three legs that happen one after another, and each leg gets its own multivariate XGBoost model. That way each model learns what actually drives its stage.

    › XGBoost · Scikit-learn
  4. Hyperparameter tuning

    Each component's model is tuned with GridSearchCV under cross-validation, so the chosen settings hold up on data the model hasn't seen.

    › GridSearchCV · Scikit-learn · XGBoost
  5. Aggregation into the final estimate

    The three predictions are added together to give the delivery time shown to the customer. Because the estimate is a sum, you can see which leg contributes the most delay.

    › Pandas · NumPy
  6. Serving & compliance baseline

    Predictions are served through FastAPI endpoints. The success metric is compliance: the share of orders that actually arrive within the promised timeframe. The baseline sits at 73%, and the work now is pushing that number up.

    › FastAPI · Pydantic · pipeline.gif ↓
02 AI-Powered Observability Platform shipped

After an incident, engineers used to spend hours digging through logs. This platform reads the logs for them. It standardises unstructured logs, stores their embeddings in ChromaDB, runs hybrid retrieval, and reranks the hits with a cross-encoder. An LLM then explains the root cause, citing the log entries behind it.

03ChromaDBembeddings
04Hybrid searchcosine ≥ 0.5
05RerankMiniLM cross-enc
06LLMroot cause
PythonLangChainChromaDB Sentence TransformersCross-encoderAzure OpenAIRAGFastAPI
  1. Log preprocessing pipeline

    Application logs arrive in mixed formats, with multi-line stack traces and severity conventions that differ from service to service. A preprocessing pipeline standardises every line into timestamp, level, service, and message, and groups each stack trace into a single record.

    › Python · Regex · Pandas
  2. Embeddings in ChromaDB

    Each structured entry is embedded and stored in ChromaDB along with its service, severity, and timestamp. Logs that describe similar failures end up close together even when the wording is completely different.

    › Sentence Transformers · ChromaDB · LangChain
  3. Hybrid search with a relevance floor

    Semantic search alone blurs exact tokens like error codes and service names. Keyword search alone misses paraphrased questions. So the platform runs both and merges the results, and a cosine similarity threshold of 0.5 drops weak matches before they reach the model.

    › ChromaDB · keyword search · LangChain retrievers
  4. Cross-encoder reranking

    Retrieval casts a wide net. A cross-encoder (ms-marco-MiniLM-L-6-v2) then scores every query–document pair together and reorders the candidates, so the most relevant evidence lands at the top of the LLM's context window.

    › Sentence Transformers · cross-encoder/ms-marco-MiniLM-L-6-v2
  5. Root-cause generation

    The reranked context goes into an engineered prompt. The LLM produces a readable explanation that points back to the actual log entries, so every claim can be traced.

    › Azure OpenAI · LangChain RAG chain · FastAPI
  6. Evaluated with the RAG Triad

    The chatbot was scored on all three RAG Triad axes: 92% context relevance, 95% groundedness, and 92% answer relevance. These scores cover whether the right evidence was retrieved, whether the answer sticks to that evidence, and whether it answers the question that was asked.

    › RAG Triad evaluation · pipeline.gif ↓
03 ML-Based Utility Cost Estimation shipped

Utility companies estimate project costs by hand, which is slow and inconsistent. This replaces the guesswork with a single multivariate XGBoost model trained on historical projects. It predicts all four cost components at once, with R² between 0.75 and 0.78 on each.

  1. Exploratory data analysis

    Distributions, outliers, missing values, and how project attributes relate to cost. The goal was to find what actually drives cost, and line the inputs up with the prediction targets, before letting a model near the data.

    › Pandas · Matplotlib / Seaborn · NumPy
  2. Feature engineering & encoding

    I built derived variables from the EDA findings, handled missing values, and encoded the categorical project attributes so the gradient-boosting model could use them.

    › Pandas · Scikit-learn
  3. Tuning with Optuna

    Grid search grows exponentially and wastes trials on dead regions. Optuna learns from earlier trials and stops bad ones early, so it finds better configurations in far fewer runs.

    › Optuna · XGBoost
  4. One multivariate model, four outputs

    A single XGBoost model predicts material, internal labour, external labour, and other or miscellaneous costs at the same time. On tabular data at this scale, gradient-boosted trees train faster than neural networks and stay interpretable. Interpretability matters for a system finance teams have to trust.

    › XGBoost · Scikit-learn
  5. Evaluation

    Held-out R² of 0.75 for material, 0.77 for internal labour, 0.78 for external labour, and 0.78 for other costs. The model explains more than three quarters of the variance in every component.

05 Lightweight CNN for Alzheimer's Classification M.Tech dissertation

Four-class Alzheimer's staging from MRI brain scans using a deliberately small three-layer CNN. Nearly every published model in this space reports high accuracy on its own dataset and quietly skips cross-dataset testing. This one holds 98% accuracy when trained on one dataset and tested on a completely different one - in both directions. Small was the design goal, not a compromise: cheap models are the ones that actually get deployed in low-resource clinical settings.

01MRI datasets2 × Mendeley
02Split 80:10:10stratified
03Augment+ SHA-256 dedup
043-layer CNN16 → 32 → 64
055-fold CVconsistency
06Cross-datasetboth directions
TensorFlowCNNAlbumentations OpenCVScikit-learnSHA-256 Medical imaging
  1. The gap I was aiming at

    I reviewed four recent CNN approaches to Alzheimer's classification - DEMNET with SMOTE, an enhanced-preprocessing CNN, an ensemble model, and TinyNet. Reported accuracies ranged from 93% to 98%, and not one of them validated across datasets. A model that only performs on its own distribution is a model that fails the moment it meets a different scanner. That gap became the thesis.

    › literature survey · IIIT Bhopal
  2. Two datasets, one severe imbalance

    Mendeley Alzheimer's (Oct 2023, 6,400 slices at 200×190) and Mendeley Advanced Alzheimer's (Jan 2025, 6,399 slices at 176×208, derived from ADNI). Same four labels, meaningfully different image characteristics - which is exactly what makes them useful for testing domain shift. Both carry a brutal imbalance: Moderate Demented is 64 images, roughly 1% of the data, against 3,200 Non-Demented.

    › Mendeley 2023 · Mendeley Advanced 2025
  3. Stratified split before anything else

    80:10:10 into train, validation, and test, stratified so each split preserves the original class distribution - critical when a class has 64 samples total. The split happens before augmentation, so augmented variants of a training image can never leak into validation or test. Test and validation stay entirely untouched.

    › Scikit-learn · stratified sampling
  4. Augmentation to balance the classes

    Applied to the training set only, bringing every class up to 2,560 samples. Horizontal flip (p=0.5) for orientation invariance. Affine transforms (p=0.9) - scaling 0.8–1.2, translation ±10%, shear ±15° - to simulate the positioning and zoom variation real MRI acquisition produces. Brightness and contrast jitter at ±20% (p=0.8) so the network doesn't overfit to one scanner's intensity profile. Random resized crop to 256×256 at 0.8–1.0 scale (p=0.7). Coarse dropout (p=0.5) masking up to eight 25×25 regions, forcing the model to use global structure instead of leaning on a single patch.

    › Albumentations · OpenCV · NumPy
  5. SHA-256 deduplication of augmented images

    Stacking five stochastic transforms will eventually produce collisions, and duplicates inflate the dataset without adding information - they just bias training toward whatever got repeated. Every augmented image is flattened to a 1-D pixel array, hashed with SHA-256, and checked against a set of previously seen hashes. Collisions are discarded and regenerated. The result is that the expanded dataset reflects genuine diversity rather than duplication, which matters most for the minority classes that needed the most synthesis.

    › hashlib · NumPy
  6. The architecture

    180×180 grayscale input into three convolutional blocks - 16, 32, then 64 filters, each 3×3 with batch normalisation, ReLU, and 2×2 max pooling. Flatten, then a 128-unit dense layer with batch normalisation and 0.5 dropout, into a 4-unit softmax. That's it. The blocks map onto a rough progression from edges and texture, to cortical boundaries and density variation, to the disease-level markers - hippocampal atrophy and ventricular enlargement.

    › TensorFlow · Keras
  7. Training configuration

    Adam at a 0.001 learning rate, batch size 64, sparse categorical cross-entropy, capped at 50 epochs. Early stopping on validation loss with patience 10, and checkpointing on validation accuracy so the evaluated model is the best one seen during the run rather than whatever the last epoch happened to produce. Both datasets converged well short of the cap.

    › TensorFlow · Keras callbacks
  8. In-dataset results and 5-fold validation

    96.88% on the 2023 dataset and 98.12% on the 2025 dataset. Stratified 5-fold cross-validation to confirm those weren't a lucky partition: mean 97.39% with 0.58 standard deviation on the first, and 97.78% with 0.14 standard deviation on the second. Moderate Demented - the 64-image class - reached perfect recall on both.

    › Scikit-learn · confusion matrices · classification reports
  9. Bidirectional cross-dataset validation

    The result the thesis exists for. Train exclusively on 2023, test on the entire unseen 2025 set: 98%. Reverse it - train on 2025, test on all of 2023: 98% again. No fine-tuning, no adaptation, test sets left unaugmented. A model exploiting scanner artifacts or population quirks collapses under this. Holding accuracy in both directions is evidence the network learned neurodegenerative features that transfer.

    › custom evaluation harness · Scikit-learn
  10. Benchmarked against the standard backbones

    Same splits, same augmentation, same optimiser, against VGG16, MobileNetV2, DenseNet121, ResNet50, and EfficientNetB0. None cleared 73%; EfficientNetB0 and ResNet50 sat at chance on the second dataset. Pre-trained ImageNet features transfer poorly to grayscale MRI at this data scale, and the three-layer network trained from scratch beat all five by more than 24 points.

    › TensorFlow · Keras Applications
  11. Defended

    Submitted as my M.Tech dissertation at IIIT Bhopal under Dr. Akhilendra Pratap Singh and Dr. Deep Chandra Joshi. Viva held July 2026. Open questions I'd still like to close: 3D volumes instead of 2D slices, datasets beyond Mendeley, and an actual clinical deployment to find out what latency and memory really cost.
