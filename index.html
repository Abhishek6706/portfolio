01 AI-Ops Observability Platform in production

Engineers used to spend hours digging through logs after an incident. This platform reads them instead - parsing unstructured logs into records, embedding them, and using hybrid retrieval plus an LLM to explain the root cause with the supporting evidence cited.

PythonLangChainAzure OpenAI Vector DBFastAPIRAGRegex
  1. Log collection & format study

    Started with raw application and infrastructure logs - mixed formats, multi-line stack traces, inconsistent severity conventions across services. Studied the patterns before writing a single parser.

    › Python · re
  2. Structuring pipeline

    Automated parsing of every line into timestamp, level, service, and message. Multi-line stack traces get grouped into single coherent records rather than fragmenting across rows.

    › Python · Regex · Pandas
  3. Vector embeddings

    Each structured entry becomes an embedding, so logs describing similar failures sit near each other in vector space even when the wording differs completely.

    › Azure OpenAI · Hugging Face · LangChain
  4. Vector store with metadata

    Embeddings stored alongside service name, severity, and timestamp, organised into collections - a searchable semantic memory of everything that has gone wrong.

    › ChromaDB / Qdrant · LangChain
  5. Hybrid retrieval

    Semantic search alone blurs exact tokens like error codes and service names; keyword search alone misses paraphrased questions. Running both and merging the ranked results fixed the failure mode on either side.

    › LangChain retrievers · vector similarity · custom ranking
  6. Root-cause generation

    Retrieved context is injected into an engineered prompt. The LLM reads the evidence and produces a human-readable explanation grounded in actual log entries - traceable, not invented.

    › Azure OpenAI · LangChain RAG chain
  7. Chatbot & API layer

    Engineers query their logs in plain English through a conversational interface, with the whole pipeline served behind REST endpoints. Next phase: predictive analytics that flag failures before they land.

    › FastAPI · LangChain memory · Pydantic
02 Survey Analytics Platform shipped

Raw survey responses rarely speak for themselves. This platform turns them into business insight - regression and correlation across 10+ question types, click heatmaps, second-by-second video rating analysis, and GenAI classification of open-text answers, all served as REST APIs.

MongoDBPandasScikit-learn OpenCVAzure OpenAIPydanticFastAPI
  1. Ingestion from MongoDB

    Survey responses, image click coordinates, per-second video ratings, and open-text answers all live in MongoDB. Step one was pulling the right collections into Python.

    › PyMongo
  2. Transformation pipeline

    The documents arrive as nested JSON, unusable for analytics. Built a pipeline that flattens them into one row per respondent, one column per question - a consistent shape every downstream module can rely on.

    › Pandas · NumPy
  3. Cleaning

    Null handling, dtype correction, duplicate removal, value normalisation. Unglamorous, but every statistic computed later depends on getting this right.

    › Pandas · NumPy
  4. Type-aware encoding

    Survey answers are mostly categorical. Encoding strategy varies by question type - label encoding where order is meaningful, one-hot where it isn't.

    › Scikit-learn · Pandas
  5. Regression & correlation module

    Users pick input and output questions; the module fits regressions and computes correlation coefficients across 10+ question types to surface what actually drives the outcome.

    › Scikit-learn · SciPy · NumPy
  6. Click heatmaps

    For image questions, aggregates every respondent's click coordinates into a density grid and overlays it on the original image - hot regions and dead zones become obvious instantly.

    › NumPy · OpenCV · Matplotlib / Seaborn
  7. TubePulse video analytics

    Respondents rate videos continuously while watching. TubePulse plots the rating for every second of playback, exposing the exact moments that gained or lost the audience.

    › Pandas · NumPy · Matplotlib / Plotly
  8. Semantic classification of open text

    Free text can't be encoded like a category - meaning matters. An LLM classifies each response into four categories, with Pydantic-enforced structured output so downstream analytics always receive valid JSON.

    › Azure OpenAI · prompt engineering · Pydantic
  9. REST API layer

    Every module exposed as a production endpoint, with continuous learning as new responses land in MongoDB - insights reflect current data rather than a stale snapshot.

    › FastAPI · Pydantic · Uvicorn
03 Utility Cost Estimation Engine shipped

Utility companies estimate project costs manually - slowly and inconsistently. This replaces the guesswork with models trained on historical project data, positioned as an integration layer between design inputs and the finance system.

XGBoostOptunaScikit-learn PandasEDAFastAPI
  1. Historical data loading

    Gathered project attributes paired with their actual costs across four separate cost output variables.

    › Pandas · NumPy
  2. Exploratory data analysis

    Distributions, outliers, missing values, and the relationships between attributes and cost. The point was deciding what actually drives cost before letting a model near the data.

    › Pandas · Matplotlib / Seaborn · NumPy
  3. Feature engineering

    Derived variables built from EDA insight, missing values handled, and the most predictive attributes selected separately for each of the four outputs.

    › Pandas · NumPy
  4. Categorical encoding

    Project attributes converted to numeric form via label encoding so the gradient-boosting model could consume them.

    › Scikit-learn
  5. XGBoost training

    One regressor per cost variable. Gradient-boosted trees beat neural networks on tabular data at this scale, train faster, and stay interpretable - which mattered for a system finance teams need to trust.

    › XGBoost · Scikit-learn
  6. Tuning with Optuna

    Grid search scales exponentially and wastes trials on dead regions. Optuna's Bayesian-style search learns from previous trials and prunes bad ones early - better configurations in far fewer runs, across four separate models.

    › Optuna · XGBoost
  7. Evaluation

    R² above 0.75 on held-out data for all four cost variables - the models explain more than three quarters of the variance in project cost.

    › Scikit-learn · Matplotlib
  8. Integration layer

    Trained models served as the bridge between design inputs and the finance system, automating the end-to-end estimation process.

    › FastAPI · Pandas
04 Lightweight CNN for Alzheimer's Classification M.Tech dissertation

Four-class Alzheimer's staging from MRI brain scans using a deliberately small three-layer CNN. Nearly every published model in this space reports high accuracy on its own dataset and quietly skips cross-dataset testing. This one holds 98% accuracy when trained on one dataset and tested on a completely different one - in both directions. Small was the design goal, not a compromise: cheap models are the ones that actually get deployed in low-resource clinical settings.

TensorFlowCNNAlbumentations OpenCVScikit-learnSHA-256 Medical imaging
  1. The gap I was aiming at

    I reviewed four recent CNN approaches to Alzheimer's classification - DEMNET with SMOTE, an enhanced-preprocessing CNN, an ensemble model, and TinyNet. Reported accuracies ranged from 93% to 98%, and not one of them validated across datasets. A model that only performs on its own distribution is a model that fails the moment it meets a different scanner. That gap became the thesis.

    › literature survey · IIIT Bhopal
  2. Two datasets, one severe imbalance

    Mendeley Alzheimer's (Oct 2023, 6,400 slices at 200×190) and Mendeley Advanced Alzheimer's (Jan 2025, 6,399 slices at 176×208, derived from ADNI). Same four labels, meaningfully different image characteristics - which is exactly what makes them useful for testing domain shift. Both carry a brutal imbalance: Moderate Demented is 64 images, roughly 1% of the data, against 3,200 Non-Demented.

    › Mendeley 2023 · Mendeley Advanced 2025
  3. Stratified split before anything else

    80:10:10 into train, validation, and test, stratified so each split preserves the original class distribution - critical when a class has 64 samples total. The split happens before augmentation, so augmented variants of a training image can never leak into validation or test. Test and validation stay entirely untouched.

    › Scikit-learn · stratified sampling
  4. Augmentation to balance the classes

    Applied to the training set only, bringing every class up to 2,560 samples. Horizontal flip (p=0.5) for orientation invariance. Affine transforms (p=0.9) - scaling 0.8–1.2, translation ±10%, shear ±15° - to simulate the positioning and zoom variation real MRI acquisition produces. Brightness and contrast jitter at ±20% (p=0.8) so the network doesn't overfit to one scanner's intensity profile. Random resized crop to 256×256 at 0.8–1.0 scale (p=0.7). Coarse dropout (p=0.5) masking up to eight 25×25 regions, forcing the model to use global structure instead of leaning on a single patch.

    › Albumentations · OpenCV · NumPy
  5. SHA-256 deduplication of augmented images

    Stacking five stochastic transforms will eventually produce collisions, and duplicates inflate the dataset without adding information - they just bias training toward whatever got repeated. Every augmented image is flattened to a 1-D pixel array, hashed with SHA-256, and checked against a set of previously seen hashes. Collisions are discarded and regenerated. The result is that the expanded dataset reflects genuine diversity rather than duplication, which matters most for the minority classes that needed the most synthesis.

    › hashlib · NumPy
  6. The architecture

    180×180 grayscale input into three convolutional blocks - 16, 32, then 64 filters, each 3×3 with batch normalisation, ReLU, and 2×2 max pooling. Flatten, then a 128-unit dense layer with batch normalisation and 0.5 dropout, into a 4-unit softmax. That's it. The blocks map onto a rough progression from edges and texture, to cortical boundaries and density variation, to the disease-level markers - hippocampal atrophy and ventricular enlargement.

    › TensorFlow · Keras
  7. Training configuration

    Adam at a 0.001 learning rate, batch size 64, sparse categorical cross-entropy, capped at 50 epochs. Early stopping on validation loss with patience 10, and checkpointing on validation accuracy so the evaluated model is the best one seen during the run rather than whatever the last epoch happened to produce. Both datasets converged well short of the cap.

    › TensorFlow · Keras callbacks
  8. In-dataset results and 5-fold validation

    96.88% on the 2023 dataset and 98.12% on the 2025 dataset. Stratified 5-fold cross-validation to confirm those weren't a lucky partition: mean 97.39% with 0.58 standard deviation on the first, and 97.78% with 0.14 standard deviation on the second. Moderate Demented - the 64-image class - reached perfect recall on both.

    › Scikit-learn · confusion matrices · classification reports
  9. Bidirectional cross-dataset validation

    The result the thesis exists for. Train exclusively on 2023, test on the entire unseen 2025 set: 98%. Reverse it - train on 2025, test on all of 2023: 98% again. No fine-tuning, no adaptation, test sets left unaugmented. A model exploiting scanner artifacts or population quirks collapses under this. Holding accuracy in both directions is evidence the network learned neurodegenerative features that transfer.

    › custom evaluation harness · Scikit-learn
  10. Benchmarked against the standard backbones

    Same splits, same augmentation, same optimiser, against VGG16, MobileNetV2, DenseNet121, ResNet50, and EfficientNetB0. None cleared 73%; EfficientNetB0 and ResNet50 sat at chance on the second dataset. Pre-trained ImageNet features transfer poorly to grayscale MRI at this data scale, and the three-layer network trained from scratch beat all five by more than 24 points.

    › TensorFlow · Keras Applications
  11. Defended

    Submitted as my M.Tech dissertation at IIIT Bhopal under Dr. Akhilendra Pratap Singh and Dr. Deep Chandra Joshi. Viva held July 2026. Open questions I'd still like to close: 3D volumes instead of 2D slices, datasets beyond Mendeley, and an actual clinical deployment to find out what latency and memory really cost.
